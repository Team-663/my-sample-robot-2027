# Harness Guide

How our AI harness works, and how to change it safely. For students and mentors who maintain the harness this season. If you only want to build robot code, read [Add a mechanism](../guides/add-a-mechanism.md) instead.

The **harness** is everything that steers and checks AI-assisted work in this repo: the instruction files Copilot reads, the reference example it copies, the Spec Kit templates, the editor safety settings, CI, and the review rules. What we build and when is in the [phase plan](phase-plan.md); why is in the [decision log](decisions.md).

## Three ideas to keep in mind

1. **Copilot copies examples more reliably than it follows prose.** The reference subsystem (`subsystems/exampleroller/` + `specs/000-example-roller/`) is our strongest instruction. A pattern bug there spreads into every mechanism, so changes to it get the most careful review.
2. **Every line in an always-loaded file costs credits on every request.** `AGENTS.md` and `.github/copilot-instructions.md` are sent with every chat message. Keep them short. Put rules that only apply to some files in a path-specific instructions file, which loads only for matching files.
3. **Instructions are requests; checks are enforcement.** An instruction can be ignored. A failing CI check, a required review, or a hook that blocks a command cannot. When a rule really matters (safety, tests), back it with a check.

## Rules for every harness change

1. **Is there a reason now?** A fix for something broken, or a [phase plan](phase-plan.md) Phase 1 item whose **trigger** has fired. "It would be nice" is not a trigger. Write the reason in the PR.
2. **One item per PR**, on its own branch, titled `Harness: <what>`. Small PRs get reviewed quickly.
3. **Never loosen safety.** No removing deny rules, weakening tests or CI, or dropping review requirements. If you believe one is wrong, open an issue and discuss it with a mentor first.
4. **Record decisions.** If the change alters a decision in [`decisions.md`](decisions.md), add a new entry that supersedes the old one. Don't edit history.
5. **Update the trackers.** Change the item's status in the [phase plan](phase-plan.md). If you add or move a harness file, update the table above.
6. **Test it** (next section) and say in the PR how you tested it.
7. **Mentor review.** CODEOWNERS requires it for `AGENTS.md`, `.github/`, `.specify/`, `docs/framework/`, and the reference example.

## How to test a harness change

| You changed | How to test it |
|---|---|
| An instruction file (`AGENTS.md`, `*.instructions.md`, copilot-instructions) | Start a **new** Copilot chat in Agent mode and ask something that should trigger the rule (for example, "add a SmartDashboard value for the roller state"). Expand **References** under the reply to confirm your file was loaded, then check that the answer follows the rule. Paste the prompt and result in the PR. |
| The spec template | `python3 .specify/scripts/python/resolve_template.py spec-template` prints the template Spec Kit will use. Check that your change is in it. |
| The reference subsystem | `./gradlew build` (all tests pass), then the sim steps in the [README](../../README.md#quick-start-about-10-minutes-after-setup). Update spec 000 in the same PR. |
| CI | Push the branch and open a PR: the workflow runs on it. Check the run's log, not just the green tick. |
| Terminal deny rules | In a new chat, ask Copilot to run the blocked command. It must stop and ask you. Click **Skip**. |
| A hook (Phase 1) | Same as deny rules, but the command must be **blocked**, not just paused for approval. |

## Recipes

### A. Copilot keeps making the same mistake

The phase plan's trigger is "the same mistake shows up in 2+ agent PRs".

1. Find the smallest place the fix can live:
   - The mistake is in code that copies the reference? **Fix the reference** (recipe G). This fixes it for good.
   - It's a 2027 API mistake? Add one line to the **2027 API pitfalls** list in `AGENTS.md`.
   - It only applies to one kind of file (tests, commands, IO classes)? Use a **path-specific instructions file** (recipe B).
2. Write the rule as a concrete do/don't with the correct name, e.g. "Enable queries are on `RobotState`, not `DriverStation`". Vague rules ("be careful with timestamps") don't change behavior.
3. Test it in a fresh chat with the prompt that went wrong before.

### B. Add a path-specific instructions file

Create `.github/instructions/<topic>.instructions.md`. Copy the shape of the existing [`framework-docs.instructions.md`](../../.github/instructions/framework-docs.instructions.md):

```markdown
---
name: Transition test rules
description: Use when writing or editing subsystem transition tests.
applyTo: "src/test/java/first/robot/subsystems/**"
---

# Transition tests

- One test per transition-table row, named after the row: `t3_stallDetectedGoesStalled`.
- Call `nextState` directly. Do not start the simulator or the HAL in transition tests.
- Use named boolean constants (`ENABLED`, `NO_PIECE`), as in `ExampleRollerTransitionTest`.
```

Keep it under about 20 lines, and point at a real file to copy rather than describing the pattern in words. `applyTo` is a glob; test it by editing a matching file in a fresh chat and checking References.

### C. Add or change a CI check

1. **Make it a Gradle task first**, so students can run exactly what CI runs on their laptops. CI should only call `./gradlew <task>`.
2. Add it as a step in the existing `build` job of `.github/workflows/build.yml`, or as a new job if it is slow (sim scenarios, replay).
3. Pin actions to a major version (`@v6`) from the action's official repo. Only use actions from `actions/`, `gradle/`, or other well-known publishers.
4. Keep `permissions: contents: read` unless the job truly needs more, and say why in a comment.
5. A new job is a new status check name. After it passes on a PR, a repo admin adds it to the `main` ruleset (setup guide Part 6), and you add a row to the phase plan.

### D. Add a skill (`frc-*`)

The trigger: the same multi-step prompt has been typed 3+ times.

1. Create `.github/skills/frc-<name>/SKILL.md`. The frontmatter `name` must match the folder name:
   ```markdown
   ---
   name: "frc-<name>"
   description: "One sentence: what it does and when to use it. Copilot uses this to decide when it applies."
   ---

   ## Steps
   1. ...
   ```
2. Write steps as a checklist that names real files and commands. Keep it short: the whole file loads when someone runs `/frc-<name>`.
3. A skill must never deploy, write NetworkTables, or push. If it runs commands, list them so a reviewer sees them.
4. Test: type `/frc-<name>` in a new chat and run it on a real task.

### E. Change the spec template

Edit **only** [`.specify/templates/overrides/spec-template.md`](../../.specify/templates/overrides/spec-template.md). The core file `.specify/templates/spec-template.md` belongs to Spec Kit, and an upgrade would overwrite your change there (D-016).

1. Edit the override.
2. Update [`specs/000-example-roller/spec.md`](../../specs/000-example-roller/spec.md) so the reference shows the new field filled in.
3. Test with the resolver command in the testing table.
4. If the field adds a review item, update the [review checklist](../guides/review-checklist.md).

### F. Change the constitution

1. Edit `.specify/memory/constitution.md` in its own PR.
2. Bump the version at the bottom: MAJOR for a removed or redefined principle, MINOR for a new principle, PATCH for wording. Update **Last Amended**.
3. Add a decision entry and get mentor approval.
4. If a principle changed, check `AGENTS.md` still agrees with it.

### G. Change the reference subsystem

1. Change the spec first (`specs/000-example-roller/spec.md`), then the code, then the tests, in one PR.
2. Keep it small. It is a teaching example, not a real mechanism. Add a pattern only if every mechanism needs it (the stall debounce is an example).
3. `./gradlew build` and a sim check. Explain in the PR why every future mechanism should copy the change.
4. Look for mechanisms that already copied the old pattern and open an issue for each.

### H. Add a hook (Phase 1)

Trigger: before students run agent mode unsupervised. Hooks are a VS Code **Preview** feature, so check the current [VS Code hooks docs](https://code.visualstudio.com/docs/agent-customization/hooks) when you build this; the format may have changed.

1. Plan (from [framework §6](agentic-dev-framework.md#6-copilot-customization-map)): hook files in `.github/hooks/`; a `preToolUse` hook denies deploy, NetworkTables writes, and force-push by returning `permissionDecision: "deny"`.
2. Keep the hook script tiny, with no network calls, and running on Windows, macOS, and Linux.
3. Keep the `.vscode/settings.json` deny rules as a second layer.
4. Test every blocked command (deploy, `git push --force`, an NT write) in a fresh chat on each OS the team uses. Update D-006.

### I. Upgrade WPILib and vendordeps

Plan one upgrade day for WPILib **and** all vendordeps together (for example, when 2027 Beta 1 ships).

1. New branch. Install the new WPILib with its installer (setup guide 2.2).
2. Update the GradleRIO version in `build.gradle` (the `org.wpilib.GradleRIO` plugin line).
3. Update each vendordep through **WPILib: Manage Vendor Libraries → Check for updates**. Never hand-edit or copy JSON from an older year.
4. `./gradlew clean build`, then the sim check.
5. Read the release notes for API changes. Add any new pitfall to `AGENTS.md`, and remove pitfalls that no longer apply.
6. If the Java version changed, update `build.gradle` and `java-version` in `build.yml` together.
7. Update the version pins in the setup guide, and tell everyone to install the new WPILib before pulling.

### J. Upgrade Spec Kit

We pin Spec Kit v1.4.0 (D-014) so it doesn't change mid-season.

1. New branch. Read the Spec Kit release notes between our version and the new one.
2. Install the new CLI version and re-run the integration as in setup guide 5.2.
3. Review `git diff` carefully: the constitution, the template override, and `specs/` must be **unchanged**. Restore anything the upgrade overwrote.
4. Run the template resolver test, then `/speckit-specify` on a throwaway feature in a fresh chat, and delete the result.
5. Add a decision entry superseding D-014.

### K. Pull any other Phase 1 item forward

1. Confirm the trigger in the [phase plan](phase-plan.md#phase-1--add-when-the-work-needs-it-build-season) has fired, and say how in the PR.
2. Read the relevant section of [`agentic-dev-framework.md`](agentic-dev-framework.md) for the original design, and [`archive/build-pieces.md`](archive/build-pieces.md) for the old acceptance criteria. Take only what the current need requires.
3. Build the smallest version that meets the need. Follow the rules above.
4. Move the row from the Phase 1 table to "Done in Phase 1" in the phase plan, with the PR number.

## Things we decided not to do

So nobody re-litigates them by accident. Details in the [decision log](decisions.md).

- No auto-approved terminal commands and no Agent Merge (D-006, AGENTS.md).
- No automatic Copilot code review; mentors request Lite reviews (D-013).
- No OpenCode as the team harness (D-017).
- No Commands v3 pilot branch; v3 is decided at Kickoff (D-003, D-016).
- No hand edits to generated Spec Kit skills or the core templates.
